463: 8. Functional Requirements
464: 
465: 8.1 Master Data Management
466: All master data is managed by the Admin role. Excel bulk upload is supported for all entities for initial population and ongoing maintenance. All entities support Active/Inactive flag.
467: 
468: 8.1.1 Product Master & BOM
469: The product master and BOM configuration are a single entity. Each product record contains:
470: Product Code: Unique SKU identifier (e.g., M159-410-000-WWC)
471: Description: Full product name
472: Product Type: Enumerated: Payment Terminal | Accessory | Battery
473: Product Category: PaymentDevice | SerializedAccessory | Accessory
474: Serialised: Boolean — if Yes, tracked at serial number level; if No, tracked by count only
475: Unit Value: Standard cost with currency
476: Refurbished Unit Value: Optional — cost for refurbished units
477: Applicable Countries: Multi-select list of countries (from a country reference list) where this product is applicable. Replaces free-text Regions field.
478: Interchangeable Products: Multi-select links to other Product records in the Product Master — not free text. Used for substitution during ATP.
479: HS Harmonised Code: Optional — customs classification code
480: Is BOM: Boolean — if Yes, this product is a kit/box containing multiple components
481: BOM Components: If Is BOM = Yes: a list of component product codes with quantities. Admin can add or remove components from the BOM configuration.
482: Supplier(s): Many-to-many link to Supplier Master — multiple suppliers per product
483: Authorised Repair Centres: List of Location records (type = Repair Centre) that are authorised to repair this product. Used in Repair Order routing.
484: Active/Inactive: Flag to deactivate without deletion
485: 
486: Note: Excel bulk upload supports initial population. Product Code must be unique. BOM component product codes must already exist in the master.
487: 
488: 8.1.2 Supplier Master
489: Each supplier record contains: Supplier Code, Supplier Name, Country, City, Contact Details (optional), and a read-only list of Products Supplied (derived from Product Master linkage).
490: 
491: 8.1.3 Location (Warehouse & FSL) Master
492: Each location record contains:
493: Location Code: Unique short code (e.g., Oostrum, DHLAU, FSLUK)
494: Location Name: Full descriptive name
495: Country & City: Physical address
496: Location Type: Selectable from a configurable type list (maintained by Admin). Default types: Warehouse, FSL, Repair Centre, Supplier. Admin can add or rename types without code changes.
497: Region Served: Geographic service area description
498: Reporting Currency: The currency to which all activity costs at this location are normalised for reporting (e.g., EUR for Oostrum, USD for Memphis). Set per location.
499: Active/Inactive: Flag
500: 
501: 8.1.4 Transit Time Master
502: Transit times are maintained as a standalone entity, separate from the Location Master. Each transit time record covers a specific lane:
503: From Location: Origin (warehouse, FSL, or supplier)
504: To Location: Destination (warehouse, FSL, or customer region)
505: Transport Mode: Air | Sea | Road
506: Lead Time (Days): Number of calendar days for this lane and mode
507: Lanes are maintained in a grid view (From × To). If no lane is defined, the system uses a configurable global fallback lead time (default: 14 days, set by Admin). The transit time master feeds the ATP calculation engine.
508: Note: Transit time applies to: warehouse-to-warehouse (Distribution Orders), warehouse-to-customer (Sales/Rental/Replacement Orders), and supplier-to-warehouse (inbound ETA estimation).
509: 
510: 8.1.5 Assembly Time Master
511: Assembly time is the number of days required to consolidate BOM components at a single location before shipment, when not all components are co-located. Configured per location (e.g., Oostrum = 2 days). Used in ATP calculation for kit orders where sourcing from multiple locations is required.
512: 
513: 8.1.6 Customer Master
514: Each customer record contains:
515: Customer ID: Unique internal identifier
516: DUNS Number: Optional — standard business identifier
517: Customer Name: Legal or trading name
518: Customer Type: Shop | Merchant | Distributor | Partner
519: Country & State/Region: Location details
520: Credit Rating: Optional — for risk flagging on outbound orders
521: Delivery Address: Default ship-to address
522: Contact Details: Email, phone (optional)
523: Active/Inactive: Flag

755: 8.3.2 Serial Number Import (Inbound File Upload)
756: When a supplier ships goods, they provide a file containing the serial numbers of shipped terminals linked to the PO. This file can be uploaded by: the Supplier (via their limited-access portal), the Supply Planner, or the Warehouse User.
757: 
758: Required fields in upload file:
759: Serial Number: The terminal serial number
760: Product Code: SKU of the terminal
761: Inbound Shipment Reference: Supplier's shipment or delivery note reference
762: Carrier: Name of the carrier handling the shipment
763: Estimated Date of Arrival: Expected date at the destination warehouse
764: Carrier Tracking Reference: Carrier-issued tracking number
765: 
766: Import processing rules:
767: The user selects the relevant PO before uploading the file, or the PO ID is included in the file.
768: The system parses each row and creates a serial number record with state = EXPECTING, linked to the PO and the carrier/ETA details.
769: Uniqueness check: a serial number is considered a duplicate if the same SerialNumber + Supplier combination already exists in the system. Duplicate rows are rejected with a per-row error report.
770: Non-duplicate serials are created; the PO status updates to Expected.
771: The Expecting view is updated to show: serial number, product, PO reference, inbound shipment reference, carrier, ETA, and destination warehouse.
772: 
773: Note: The import template (Excel) is downloadable from the Upload Centre view.

775: 8.3.3 Warehouse Receipt Confirmation
776: The PO Detail view shows a three-column qty summary per line: Qty Ordered | Qty Expected (serials uploaded) | Qty Received (confirmed by warehouse). This allows the warehouse user to identify any shortfall at a glance.
777: 
778: Receipt confirmation flow:
779: Warehouse User opens the PO Detail view from the Expecting view.
780: User confirms receipt — individually per serial, or via mass confirmation of all expected serials under the PO.
781: Confirmed serials transition from EXPECTING to QUARANTINE. Receipt date and location are recorded.
782: The PO line Qty Received count increments. PO status updates to Partially Received or Fully Received.
783: If the received quantity is less than the Qty Expected, the remaining serials stay in EXPECTING state. The delta is visible in the PO Detail view.
784: 
785: R2: If the received quantity is less than expected (missing) or terminals arrive damaged, the Warehouse User can create a Claim against the supplier or logistics carrier. Claim types (e.g., Missing, Damaged, Wrong Item) are configurable by Admin. Claim management is a Release 2 feature.

852: 8.4.3 Box/Kit Fulfillment & ATP Check
853: Every outbound order triggers an ATP (Available-to-Promise) check. The ATP engine:
854: Checks AVAILABLE inventory of each order line at the preferred fulfillment location (or nearest available location).
855: For BOM/kit products: expands the BOM into components and checks each component's availability.
856: If all components are co-located: ATP date = today + transit time (from Transit Time Master) to customer.
857: If components are split across locations: the engine identifies the missing components, checks alternate locations, and calculates: transit time to consolidate at fulfillment location + assembly time (from Assembly Time Master) + transit time to customer.
858: The ATP result is displayed to the Supply Planner showing: fulfilling location, expected ship date, expected delivery date.
859: The Supply Planner can adjust order quantity or date. Each adjustment triggers a recalculation. If the requested date is not achievable, a red warning message is displayed: 'ATP infeasible — earliest possible delivery is [date].' The Supply Planner can acknowledge the warning and proceed with their own date (override decision recorded).
860: 
861: Note: Specific serial number allocation happens at the Allocated status, not at order creation. ATP confirms count feasibility only.
862: R2: When components must be sourced from multiple locations, the system will in Release 2 automatically generate a Work Order sent to the relevant Warehouse User, instructing them to prepare the assembly.

867: Rental Fee: Rental charge amount and currency.
868: Expected Return Date: Automatically calculated as Shipped Date + Rental Period. Tracked and visible in the Order Detail view.

872: 8.4.5 Replacement Orders
873: Replacement Orders are auto-drafted by the system when a Return Order reaches Initiated status (see 8.5.1). The auto-drafted Replacement Order is pre-populated with:
874: Same customer as the Return Order
875: Same product as the returned terminal (or the best available alternative product if the same product has zero AVAILABLE inventory)
876: Same source warehouse as the originating outbound order
877: The auto-draft appears in the Supply Planner's queue for review and issuance. The Supply Planner can adjust product, quantity, or source location before issuing. The Replacement Order is linked to the Return Order by reference and both are visible from each other's detail views.

879: 8.5 Return & Repair Flow
880: 
881: 8.5.1 Return Order
882: A Return Order (RExxxxxx) is created when a customer returns a terminal. Return Order fields:
883: Return Order ID: RExxxxxx
884: Original Order Reference: Linked Sales or Rental Order
885: Customer: Derived from original order
886: Serial Number(s): Terminals being returned
887: Reason: Defective | End of Rental | End of Lifecycle | Wrong Item | Other
888: Return Status: Initiated | In Transit | Received | Inspected | Closed
889: Inspection Outcome: Set at Inspected status — Defective or Scrap
890: Linked Replacement Order: Auto-generated reference to linked RPxxxxxx
891: 
892: Status transitions and system actions:
893: Initiated: Return Order created. System immediately auto-drafts a Replacement Order (same product, same customer, same source warehouse; alternative product if same product unavailable). Supply Planner is notified to review and issue the replacement draft.
894: In Transit: Customer has shipped the terminal back.
895: Received: Warehouse User confirms physical receipt. Terminal serial number state transitions to DEFECT.
896: Inspected: Warehouse User inspects the terminal and sets the Inspection Outcome:
897: Outcome = Defective → Warehouse User initiates a Repair Order (RRxxxxxx). Terminal state moves to UNDER_INVESTIGATION.
898: Outcome = Scrap → Terminal state transitions to SCRAP/DESTROYED. Terminal traceability ends. The terminal record is closed and marked permanently inactive. It cannot be reactivated.
899: Closed: All actions completed.
900: 
901: 8.5.2 Repair Order
902: A Repair Order (RRxxxxxx) is created from the Return Order Inspected step or directly from inventory for a defective terminal. Key fields and flow:
903: Repair Order ID: RRxxxxxx
904: Serial Number(s): Terminal(s) being repaired
905: Repair Centre: Selected from the list of Authorised Repair Centres defined on the Product Master for this product. Not all repair centres service all products.
906: Dispatch Date: Date sent to repair centre
907: Estimated Return Date: Expected date back at the originating warehouse (set by Repair Centre user on confirmation)
908: Default Return Warehouse: Same warehouse the terminal was received from (editable if needed)
909: Status: Dispatched | Received at Repair Centre | In Repair | Completed | Returned
910: Actual Repair Cost: Entered by Repair Centre user upon job completion (amount + currency)
911: 
912: Repair flow:
913: Warehouse User creates Repair Order, selects authorised repair centre for the product, and dispatches. Terminal state → TRANSIT_TO_REPAIR.
914: Repair Centre User confirms receipt. Terminal state → IN_REPAIR.
915: Repair Centre User completes repair. Enters: actual repair cost, repair notes, outcome (Repaired or Beyond Repair), and confirms shipment back to warehouse with estimated date of arrival.
916: Outcome = Repaired → Terminal state → QUARANTINE_REFURBISHED at the originating warehouse upon return receipt.
917: Outcome = Beyond Repair → Terminal state → SCRAP/DESTROYED. Traceability ends.
918: Warehouse User receives terminal back and moves it to AVAILABLE_REFURBISHED after quality check.
919: 
920: Note: SCRAP and DESTROYED are the same terminal state. Once a terminal enters this state it cannot be reactivated or used in any order.

987: 9. Non-Functional Requirements
988: 
989: 
990: Category
991: Requirement
992: Performance
993: Any inventory list view must load within 3 seconds for up to 10,000 serial number records. Search and filter results must return within 2 seconds.
994: Scalability
995: Designed for hundreds of active serial numbers and dozens of concurrent orders in R1. Database schema supports migration to PostgreSQL for larger scale without application code changes.
996: Data Integrity
997: All state transitions are logged immutably with timestamp (including timezone), user, and source. No state change is permitted without a valid preceding state per the transition rules in the State Configuration master.
998: Audit Trail
999: Complete, immutable state history per serial number and complete status history per order, permanently stored and viewable.
1000: Security
1001: Username/password authentication. Passwords hashed (bcrypt). Role-based access control enforced at API level. JWT session tokens with configurable expiry. HTTPS when deployed to server.
1002: Data Import/Export
1003: Excel upload for all master data entities and all operational upload types. All list views exportable to Excel.
1004: Browser Support
1005: Chrome, Edge, Firefox (latest 2 versions). No mobile requirement in R1.
1006: Deployment
1007: R1: runs locally via a single start command (e.g., ./start.sh). R2: deployable to Linux server with documented setup instructions.
1008: Internationalisation
1009: UI in English. Currency fields support multi-currency with exchange rate normalisation. Date/time fields store timezone.
1010: Cost Normalisation
1011: All activity costs are stored in their native currency. For reporting and the accumulated cost total, costs are converted to the warehouse's reporting currency using the Exchange Rate Master.

1017: Layer
1018: Technology
1019: Rationale
1020: Frontend
1021: React + Vite
1022: Fast component-based UI. Vite provides lean local dev server. Hot reload for iteration speed.
1023: Styling
1024: Tailwind CSS
1025: Utility-first CSS with e2open colour palette (navy #003087, blue #0075C2, orange #F7941D) as custom design tokens.
1026: UI Navigation
1027: Icon-based left sidebar
1028: One icon per module. Active state highlighted in blue. Collapsed by default, expandable.
1029: Backend
1030: Python FastAPI
1031: Modern, high-performance Python API. Auto-generates OpenAPI docs. Async-capable. Easy to extend for API integration module.
1032: ORM
1033: SQLAlchemy
1034: Database-agnostic ORM. SQLite → PostgreSQL migration requires only a connection string change.
1035: Database
1036: SQLite (R1) → PostgreSQL (R2)
1037: SQLite requires zero infrastructure for local deployment. PostgreSQL migration is a one-step upgrade for server hosting.
1038: Authentication
1039: JWT (JSON Web Tokens)
1040: Stateless auth with role claims in token. Refresh token for session persistence.
1041: File Processing
1042: openpyxl (Python)
1043: Excel file parsing and export for all upload types and data exports.
1044: API Integration Stub
1045: FastAPI background tasks
1046: Placeholder endpoints prepared for R2 Logistics API GET/POST operations.

1048: 10.2 Backend Module Structure
1049: Each backend module has its own FastAPI router, SQLAlchemy models, and service layer:
1050: 
1051: auth — authentication, JWT management, role enforcement
1052: products — product master, BOM, supplier-product, repair centre linkage
1053: suppliers — supplier master CRUD
1054: locations — location master, location types configuration
1055: transit_times — transit time lane matrix
1056: assembly_times — assembly time per location
1057: customers — customer master CRUD
1058: states — configurable state definitions and transition rules
1059: activity_costs — cost master per state per location
1060: exchange_rates — exchange rate master
1061: order_numbering — ID convention configuration
1062: inventory — serial number tracking, state transitions, non-serialised counts
1063: state_history — immutable state history records
1064: purchase_orders — PO header and line management
1065: inbound — serial number file upload, import processing, uniqueness enforcement
1066: outbound_orders — Sales, Replacement, Rental, Distribution order management
1067: atp_engine — ATP calculation service using transit times + assembly times
1068: returns — Return Order management
1069: repairs — Repair Order management, repair centre routing
1070: mass_upload — bulk state update, shipment confirmation, inventory adjustment
1071: analytics — aggregated KPI queries and dashboard data
1072: api_integration — stub module for future Logistics API connectivity
